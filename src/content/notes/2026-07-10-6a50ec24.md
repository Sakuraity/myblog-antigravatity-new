今天下午给大部门分享，20 分钟，面向非技术的产运 行运 平台运营的同学。

分享内容是用 Agent 做一整套 GSB 评测的实践，是的，这个是产运很重要的活现在哈哈

反馈很热烈，远远超出了我的预期，还有好多位同学分享后私戳交流。

分享文档最先写出来的版本，是把评测集、评测标准、评测流程、跟 Agent 协作的每一步细节全部按时间线摊开，事无巨细。

写完我发现一个问题：这套流程本身建立在长期用 Trae和 Devin 的习惯上。部门里持续用这类工具的人本来就不多，大多数同学更习惯通用型 Agent，觉得 Trae 偏开发向，比较抗拒，也确实很难一下子上手。

按流水账讲，大家收获有限。讲成产品安利，又违背本意，不需要谁都换成 Trae，这没意义，内部很多通用 Agent 本身做得也不错。

但为了验证这个判断，分享前私下问了不同角色的同事，以及在即刻问了即友们，了解他们对 Manus 和 Cursor 差异的认知。

结论很直接：这类工具在非技术人群里的使用比例确实很低，但工具本身能做的事情被严重低估了。

这个判断决定了分享的方向，分享该建立在跟 Agent 协作的方法上，方法是通用的。

最终定了两个主题。

第一个是怎么跟 Agent 协作让它产出高质量结果，核心是上下文管理。

挑了几个容易被忽略、日常操作里天天在做却没意识到会拖累结果的小习惯，配截图和 GIF 逐个还原操作现场，再从原理层面解释为什么这些操作会导致上下文爆炸或者注意力分散。

第二个是怎么让 Agent 稳定完成复杂任务。

工作一旦涉及自动化和批量重复性内容，需求就不再是要一个答案那么简单，而是一整套任务流。

这部分讲了 Sub-agent 架构，画图讲清楚什么是 Multi-agent，为什么要引入 Sub-agent，能解决之前遇到的哪些不稳定问题。

两个主题的共同点是都不依赖具体工具或模型，纯粹是使用习惯和协作思维上的差异。

复盘下来这次我讲的最好的地方，是把复杂的东西讲得让人接得住。

每个技巧都从操作讲到原理，解释为什么这样做会有这样的后果，而不是停在这样做就行了。
听懂原理，下次遇到类似场景才会自己判断，不用死记步骤。

技术语言翻译成常人的语言，把上下文爆炸、注意力机制这类概念，还原成大家平时协作里能对上号的具体场景。

用截图和 GIF 还原操作现场，让人看到具体是怎么做的，而不是只听一句我做了什么。

这一次我心态上也有个转变，先想清楚要落在哪两件事上，再把每件事拆到足够简单直接，取代了想要一次性讲很多东西的心态。

复杂项目能做成，靠的往往是一堆基础技能的积累。把基础技能讲透，比堆砌高级案例更有效。

讲专业内容给非专业听众之前，先做小范围调研，搞清楚对方的认知起点和顾虑，别假设他们应该也懂或者应该也关心工具本身。

遇到讲工具还是讲方法的纠结时，选方法。方法是可迁移的，工具是会过时的，听众也更容易在自己的场景里对号。

共勉！
